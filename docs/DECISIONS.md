# Architecture decisions

The decisions that shaped Khabar after the planning session, with why and what was rejected. The
planning-session choices themselves are in [plan.md §14](../plan.md). Newest last.

| Date | Decision | Why | Rejected |
|---|---|---|---|
| 22 Sep | **The report draft is built by a parser, not an LLM.** Diagnosis, plan, follow-up and every prescription line come from the doctor's shorthand (`report_agent.py`, `prescription.py`). | A model that drafts can invent a drug or a dose. A parser can only miss one, and the grounding check flags anything not in the notes. | An LLM draft checked by a second LLM: an AI checking an AI, with no ground truth. |
| 22 Sep | **A critical finding is blocked three times:** the screen, the API and a database rule. | A bug in any one layer must not let an unsafe visit be finalised. | UI-only blocking. |
| 22 Sep | **Triage is word lists or a model, whichever is more urgent.** The model may raise a reply, never lower it; negation is ignored on purpose ("tak pening" still alerts). | A false alarm costs a phone call; a missed emergency costs far more. | Model-only triage (fails silently when the provider is down), keyword-only triage (see 24 Sep). |
| 22 Sep | **Patients only hear fixed or approved words:** 999 advice for red flags, answers a doctor approved, or an acknowledgement. | The product must never give new medical advice. | Free-text model replies to patients. |
| 22 Sep | **Invite codes link sign-ins to records;** no staff self-sign-up. Codes are hashed and expire after 7 days. | A stranger with an email address must not become a doctor or see a record. | Open sign-up with a role picker. |
| 22 Sep | **One Vercel project for both backend services** (Java container + Python) in Singapore, plus one for the web app. | One place to deploy and configure the backend; the web app deploys separately and holds no backend secrets. | Separate hosts per service (more setup, more places for secrets). |
| 22 Sep | **The Next.js app replaces the static screens** generated with Antigravity (kept in `docs/` as history). | The static screens used hard-coded data; the app is wired to the API with real access rules. | Wiring the static HTML pages to the API one by one. |
| 23 Sep | **The API reaches Supabase through the transaction pooler.** | The session pooler allows 15 clients; old and new instances used them all up after a deploy and the new API could not start. | A bigger database plan. |
| 23 Sep | **Only Spring Boot writes the patient graph, under a random `graph_id`;** the agents read it, read-only. Off when `NEO4J_URI` is empty. | Identity stays in one service; a test proves no name, IC or phone reaches Neo4j. | Agents writing the graph; names as graph keys. |
| 23 Sep | **Interactions come from a reproducible DDInter 2.0 subset.** A pair missing from the data is never treated as safe. | Peer-reviewed data, re-generated by a script; honest about gaps (gliclazide has no pairs). | Letting the model judge interactions. |
| 23 Sep | **Packet photos: consent first, never stored,** the generic always comes from our own tables, and the patient reviews every item before it's added. | An image can contain a name; a misread label must not become a medicine without a person checking it. | Adding what the model reads directly. |
| 24 Sep | **The API accepts real Supabase sign-ins (ES256) and demo tokens (HS256) side by side,** each only against its own key. | The demo buttons must keep working while real sign-in is added, without a token ever being checked against the wrong kind of key (algorithm confusion). | Switching everything to real sign-in at once, which would have broken the demo. |
| 24 Sep | **AuraDB was recreated after its password was exposed.** | AuraDB Free cannot change a password; `POST /dev/graph/sync` refills it from Postgres in one call. | Keeping the exposed instance. |
| 24 Sep | **The web app deploys itself on every push to `main` that changes `web/`,** after lint and type checks. The API deploys by hand. | The newest UI goes live without a manual step, and a broken UI never does. API deploys stay deliberate. | Deploying everything on every push. |
| 24 Sep | **Every reply a person still has to read carries the 999 advice,** not only replies the word lists read as red. | Measured: the word lists raise only 2 of 12 held-out red replies ([evals](evals/README.md)). | Relying on the word lists to spot every emergency. |
| 24 Sep | **The demo reset restores Aminah's whole story,** and only what's missing or changed. | Each rehearsal starts from the same story, and a reset repairs data seeded by an older version. | Dropping and re-seeding the live database. |
| 24 Sep | **Voice-note summaries and learning each doctor's writing style stay unbuilt.** | They are last in the plan's drop order, and the P0 workflow still has real-provider work left. | Building them before WhatsApp, sign-in and triage are proven live. |
